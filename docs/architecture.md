# تصمیم نهایی معماری Dot — سند ثبت تصمیم (ADR)
**تاریخ:** ۱۷ خرداد ۱۴۰۵
**وضعیت:** قطعی — تصمیم گرفته شده، آماده‌ی پیاده‌سازی
**مبنا:** شش معیار تصمیم H + تحقیق روی الگوهای جهانی (Zillow، Datomic، Neo4j، REA، pgvector)
**اصل راهنما:** ساختن برای کاربر آینده (عامل هوشمند)، نه کاربر امروز (فیلترزننده)

---

## بخش صفر — تحلیل عمیق معیار دوم: ساختن برای آینده

این معیار را اول می‌گذارم چون کل معماری از آن بیرون می‌آید.

کاربر دیروز با بروشور تصمیم می‌گرفت. کاربر امروز در Zillow و Bayut فیلتر می‌زند. کاربر فردا تحقیق را به یک عامل هوشمند واگذار می‌کند و با او گفت‌وگو می‌کند؛ شاید هیچ‌وقت رابط کاربری Dot را هم نبیند، چون دستیار AI شخصی او ممکن است مستقیماً از طریق API یا MCP به گراف دانش Dot وصل شود و توصیه بسازد. پس مشتری اصلی معماری، یک عامل هوشمند است نه یک انسان پشت صفحه.

این بازتعریف، شکل داده را تعیین می‌کند. یک عامل هوشمند فقط وقتی می‌تواند روی داده‌ی Dot استدلال قابل‌اعتماد بکند که داده سه ویژگی داشته باشد. provenance، یعنی هر ادعا تا یک اتم و منبع قابل‌ردیابی باشد تا عامل بتواند منبعش را ذکر کند و اعتماد بسازد — همان دکترین buyer-side. structure، یعنی روابط به‌صورت گراف باشند تا عامل پیمایششان کند. semantics، یعنی معنا به‌صورت embedding ذخیره شود تا عامل بر اساس مفهوم بازیابی کند نه تطابق کلمه.

نتیجه: سنگربندی واقعی Dot نه رابط کاربری است نه listingها، بلکه یک گراف دانش تأییدشده، ساختارمند، و معنایی است که عامل‌های هوشمند آینده استدلال خریدشان را روی آن بنا می‌کنند. این همان دلیلی است که معماری باید گراف + اتم + provenance + embedding باشد — چون این دقیقاً شکل داده‌ای است که AI می‌تواند رویش ground بزند.

## بخش یک — شش معیار، شش تنظیم معماری

حالا هر معیار را به یک تصمیم معماری مشخص نگاشت می‌کنم.

**معیار یک، تناسب با پرسونای H (غیرفنی، AI-native، موبایل، خلاق).** این به یک سیستم managed واحد نگاشت می‌شود که H نیازی به مدیریت زیرساختش ندارد. Supabase دقیقاً همین است: Postgres مدیریت‌شده که H فقط با آن حرف می‌زند و Claude Code پیاده‌اش می‌کند. چند ابزار جدا (Neo4j + Elasticsearch + Datomic) یعنی سه سیستم برای نگهداری، که با پرسونای یک بنیان‌گذار تک‌نفره‌ی غیرفنی در تضاد است.

**معیار دو، ساختن برای آینده (عامل هوشمند).** این به افزودن یک لایه‌ی معنایی نگاشت می‌شود. Postgres قابلیت pgvector دارد که embedding را در همان پایگاه داده ذخیره می‌کند. پس عامل هوشمند آینده می‌تواند روی گراف دانش Dot بازیابی معنایی بکند و استدلالش را روی اتم‌های تأییدشده ground بزند — بدون نیاز به یک vector database جدا. این تصمیم، آینده‌نگری را در خود مدل داده می‌گذارد، نه در یک ابزار اضافی.

**معیار سه، بودجه (نه الان، نه آینده، بدون زیرساخت عجیب).** این به جمع‌کردن همه‌چیز در یک Postgres نگاشت می‌شود. Postgres بزرگ‌ترین جامعه‌ی متخصص دنیا را دارد (یعنی استخدام و نگهداری ارزان)، روی هر ابر اجرا می‌شود (یعنی vendor lock-in ندارد)، و pgvector و گراف و full-text را همه به‌صورت built-in دارد (یعنی هزینه‌ی ابزار اضافی صفر). Neo4j licensing دارد، Elasticsearch cluster می‌خواهد، Datomic niche است و متخصصش کم. همه‌ی این‌ها هزینه‌ی نگهداری فاجعه‌بار آینده‌اند که معیار سه منعشان می‌کند.

**معیار چهار، مقیاس‌پذیری ساده و ارزان.** Postgres مدیریت‌شده با read replica و connection pooling و partitioning مقیاس می‌گیرد، و Supabase این‌ها را خودکار می‌کند. برای مقیاس داده‌ی املاک بین‌المللی — حتی صد کشور ضربدر هزاران پروژه — Postgres سال‌ها کافی است. فقط اگر یک گلوگاه مشخص ظاهر شد (پیمایش گراف با عمق خیلی زیاد، یا جست‌وجوی برداری روی میلیاردها بردار) آن‌وقت به ابزار تخصصی می‌رویم، نه قبلش. این اصل «ساده‌ترین چیزی که کار می‌کند» است.

**معیار پنج، بین‌المللی بودن نه تک‌کشوری.** این به انتزاع jurisdiction نگاشت می‌شود. در گراف، کشور فقط یک entity_type عمومی است، نه «عمان». اتم‌ها فیلد زبان و ارز و حوزه‌ی قضایی دارند. معیارها به حوزه‌ی قضایی scope می‌شوند (یعنی یک معیار می‌تواند برای عمان طور دیگری از امارات اعمال شود، از طریق گراف applicability). این یعنی برای اضافه‌کردن کشور دوم (مثلاً امارات یا قبرس)، هیچ تغییر کدی لازم نیست — فقط یک node کشور جدید و اتم‌هایش اضافه می‌شود. معماری از روز اول بین‌المللی است.

**معیار شش، امنیت وجودی.** این مهم‌ترین تنظیم است و در بخش بعد جداگانه توضیحش می‌دهم، چون خودت گفتی اگر کسی این داده‌ها را داشته باشد دیگر ما چیزی نداریم.

## بخش دو — معماری امنیتی دو-خزانه

چون داده، خودِ شرکت است، امنیت نباید یک افزونه باشد؛ باید در ساختار باشد. راه‌حلی که هم امن است و هم برای یک بنیان‌گذار تک‌نفره قابل‌اجرا (نه over-engineered)، الگوی دو-خزانه است.

**خزانه‌ی تحقیق (private).** اینجا گراف کامل زندگی می‌کند: همه‌ی اتم‌ها، همه‌ی entityها، همه‌ی edgeها، همه‌ی روابط JV، همه‌ی provenance. این خزانه هیچ API عمومی ندارد. هیچ کاربری، هیچ عامل بیرونی، هرگز مستقیماً به آن دسترسی ندارد. فقط Prism (موتور داخلی) و عملیات داخلی به آن می‌رسند. این جواهر اصلی است — ماه‌ها تحقیق میدانی که در آن خوابیده. اگر این لو برود، رقیب همه‌چیز را کپی می‌کند.

**خزانه‌ی سرویس (public).** اینجا فقط «ماده‌ها» زندگی می‌کنند — یعنی نتیجه‌های محاسبه‌شده: پرونده‌ی پروژه، توصیه‌ی کاربر، نمای faceted. کاربر یا عامل بیرونی فقط با این خزانه از طریق یک API کنترل‌شده و rate-limited حرف می‌زند. نکته‌ی کلیدی این است که آنچه سرویس می‌شود یک نتیجه است، نه گراف خام شواهد. حتی اگر کسی کل API عمومی را scrape کند، فقط نتیجه‌ها را می‌گیرد نه substrate قابل‌استفاده‌ی اتم‌ها که موتور تحقیق را می‌سازد. موتور واقعی هرگز از خزانه‌ی private بیرون نمی‌آید.

این جداسازی، به‌طور هوشمندانه، همان مرز CQRS است که قبلاً گفتم: سمت نوشتن (اتم‌ها) در خزانه‌ی private، سمت خواندن (ماده‌ها) در خزانه‌ی public. یعنی همان تصمیمی که برای صحت داده گرفتیم، خودبه‌خود مرز امنیتی هم هست. این زیبایی معماری است: یک تصمیم، دو مزیت.

ابزارهای امنیتی که Supabase به‌صورت built-in دارد و باید فعال شوند: Row-Level Security با deny-by-default، رمزنگاری at rest و in transit، نقش‌های جدا برای خواندن و نوشتن، rate limiting روی API سرویس، و backup رمزنگاری‌شده‌ی منظم. Merkle hashing که Prism از قبل دارد، tamper-evidence (یعنی اگر کسی داده را دستکاری کند معلوم می‌شود) را تأمین می‌کند. این‌ها هیچ‌کدام exotic نیستند؛ فقط پیکربندی درست Supabase‌اند، که با معیار بودجه و پرسونا هم‌خوان است.

## بخش سه — تصمیم نهایی قطعی

با ترکیب شش معیار، تصمیم را قطعی می‌کنم. خودت گفتی به من اعتماد داری، پس این را باز نمی‌گذارم.

**یک Postgres مدیریت‌شده (Supabase)، مدل‌شده به‌عنوان یک گراف دانش تأییدشده، با چهار مؤلفه‌ی منطقی: اول انبار اتم‌های تغییرناپذیر bitemporal، دوم گراف property از entityها و edgeها، سوم رجیستری معیارها با edgeهای applicability، چهارم لایه‌ی معنایی pgvector. این چهار مؤلفه در دو خزانه تقسیم می‌شوند — خزانه‌ی تحقیق private و خزانه‌ی سرویس public. مولکول‌ها و ماده‌ها به‌صورت projectionهای محاسبه‌شده‌ی سمت خواندن ساخته می‌شوند. کشور یک entity_type عمومی برای مقیاس بین‌المللی است. بدون Neo4j، بدون Elasticsearch، بدون Datomic — هر چهار قابلیت در یک Postgres خوش‌مدل جمع شده‌اند.**

دلیل قطعی بودن این تصمیم: هر شش معیار تو را هم‌زمان برآورده می‌کند. پرسونای تو (یک سیستم managed)، آینده (pgvector برای عامل هوشمند)، بودجه (یک ابزار، بزرگ‌ترین جامعه)، مقیاس (managed Postgres)، بین‌المللی (jurisdiction انتزاعی)، امنیت (دو-خزانه با CQRS). و چون روی الگوهای اثبات‌شده‌ی Zillow و Datomic و Neo4j و REA و pgvector بنا شده، حدس نیست.

نکته‌ی خلاقانه‌ی این تصمیم — که فکر می‌کنم همان «مفهوم واقعی خلاقیت» است که خواستی — این است: خلاقیت اینجا در انتخاب ابزار پیچیده نیست، بلکه در فهمیدن این است که یک ابزار ساده و boring (Postgres) اگر هوشمندانه مدل شود، می‌تواند کار سه ابزار پیچیده را با یک‌دهم هزینه و یک‌دهم ریسک انجام دهد. خلاقیت واقعی، resist کردن وسوسه‌ی پیچیدگی است. بهترین معماری‌های دنیا آن‌هایی نیستند که بیشترین ابزار را دارند؛ آن‌هایی‌اند که با کمترین قطعه، بیشترین قابلیت را می‌سازند. این همان درسی است که Datomic (یک ایده‌ی ساده: فکت تغییرناپذیر) و Zillow (یک ایده‌ی ساده: base form در برابر concept) به ما دادند.

## بخش چهار — شکل عینی schema (طرح اولیه برای Claude Code)

برای اینکه تصمیم واقعی شود، طرح اولیه‌ی schema را اینجا می‌گذارم. این برای Claude Code است وقتی پیاده‌سازی شروع شود، و کامنت‌ها منطق پشت هر تصمیم را توضیح می‌دهند.

```sql
-- ============================================================
-- خزانه‌ی تحقیق (private schema) — جواهر اصلی، بدون API عمومی
-- ============================================================

-- جدول اتم‌ها: قلب صحت. append-only، هرگز UPDATE یا DELETE نمی‌شود.
-- هر اتم یک فکت تغییرناپذیر از یک منبع است. مدل bitemporal.
CREATE TABLE private.atoms (
    atom_id          uuid PRIMARY KEY DEFAULT gen_random_uuid(),
    entity_id        uuid NOT NULL,          -- این اتم درباره‌ی کدام موجودیت است
    criterion_id     uuid,                    -- این اتم به کدام معیار مربوط است (می‌تواند null باشد برای فکت‌های خام)
    claim            text NOT NULL,           -- خود فکت، به زبان طبیعی
    source_id        uuid NOT NULL,           -- provenance: از کدام منبع آمده
    source_class     int NOT NULL,            -- کلاس منبع (۱ تا ۴) برای وزن‌دهی اعتماد
    language         text NOT NULL,           -- زبان فکت (برای بین‌المللی بودن)
    -- دو محور زمان (bitemporal) — درس Datomic:
    valid_from       timestamptz NOT NULL,    -- کِی این فکت در دنیای واقعی درست شد
    valid_to         timestamptz,             -- کِی دیگر درست نبود (null یعنی هنوز معتبر)
    recorded_at      timestamptz NOT NULL DEFAULT now(),  -- کِی ما ثبتش کردیم
    superseded_by    uuid,                    -- اگر اتم جدیدتری منسوخش کرده، به آن اشاره می‌کند
    content_hash     text NOT NULL,           -- Merkle integrity (از Prism فعلی)
    embedding        vector(1536)             -- لایه‌ی معنایی pgvector — درس معیار دوم (آینده)
    -- چرا embedding اینجاست؟ تا عامل هوشمند آینده بتواند بازیابی معنایی کند.
);

-- جدول موجودیت‌ها: گره‌های گراف. همه‌ی لایه‌ها یکجا با entity_type.
CREATE TABLE private.entities (
    entity_id        uuid PRIMARY KEY DEFAULT gen_random_uuid(),
    entity_type      text NOT NULL,           -- 'country' | 'holding' | 'developer' | 'jv' | 'master_development' | 'unit_type' | 'operator'
    canonical_name   text NOT NULL,           -- نام نرمال‌شده (درس Zillow: concept نه base form)
    jurisdiction     text,                    -- برای بین‌المللی بودن (معیار پنج)
    status           text,                    -- برای پروژه‌ها: 'off_plan' | 'ready_turnkey' | 'ready_resale'
    embedding        vector(1536)             -- جست‌وجوی معنایی روی موجودیت‌ها هم
);

-- جدول یال‌ها: روابط گراف. شهروند درجه یک (درس Neo4j).
-- هم عمودی (contains، owns) هم افقی (joint_venture_with، operates).
CREATE TABLE private.edges (
    edge_id          uuid PRIMARY KEY DEFAULT gen_random_uuid(),
    from_entity      uuid NOT NULL,
    to_entity        uuid NOT NULL,
    edge_type        text NOT NULL,           -- 'owns' | 'joint_venture_with' | 'develops' | 'contains' | 'operates' | 'finances' | 'brands' | 'manages_post_handover' | 'regulates' | 'contractual_party_for_buyer'
    weight           numeric                  -- مثلاً درصد مالکیت در JV
);

-- جدول معیارها و صلاحیتشان: منطق مشروط به‌صورت داده، نه کد.
CREATE TABLE private.criteria (
    criterion_id     uuid PRIMARY KEY DEFAULT gen_random_uuid(),
    name             text NOT NULL,
    section          text NOT NULL            -- 'gate_board' | 'score_core' | 'developer_modifier' | 'descriptive'
);

-- این جدول می‌گوید کدام معیار برای کدام وضعیت پروژه فعال است.
-- وقتی پروژه از off_plan به ready تبدیل می‌شود، معیارهای فعالش
-- خودبه‌خود عوض می‌شوند بدون تغییر کد. (درس معیار: منطق در داده)
CREATE TABLE private.criteria_applicability (
    criterion_id     uuid NOT NULL,
    project_status   text NOT NULL,           -- 'off_plan' | 'ready_turnkey' | 'ready_resale'
    is_scoreable     boolean NOT NULL,
    PRIMARY KEY (criterion_id, project_status)
);

-- ============================================================
-- خزانه‌ی سرویس (public schema) — فقط نتیجه‌ها، API-exposed
-- ============================================================

-- مولکول: وضعیت یک معیار برای یک موجودیت. VIEW محاسبه‌شده، نه جدول.
-- همیشه از جدیدترین اتم‌ها ساخته می‌شود، پس خودبه‌خود به‌روز می‌ماند.
CREATE VIEW public.molecules AS
SELECT
    a.entity_id,
    a.criterion_id,
    -- جدیدترین اتم معتبر برای هر ترکیب موجودیت-معیار:
    (array_agg(a.claim ORDER BY a.recorded_at DESC))[1] AS current_claim,
    max(a.source_class) AS best_source_class,
    count(*) AS evidence_count
FROM private.atoms a
WHERE a.valid_to IS NULL          -- فقط اتم‌های هنوز معتبر
GROUP BY a.entity_id, a.criterion_id;
-- توجه: این VIEW فقط نتیجه می‌دهد، نه اتم خام. مرز امنیتی.

-- ماده‌ی پرونده‌ی پروژه و ماده‌ی توصیه هم به‌صورت VIEW یا
-- materialized view (اگر سرعت لازم شد) ساخته می‌شوند.
-- ماده‌ی توصیه = واکنش بین مولکول کاربر (Lens) و مولکول پروژه (Prism).
```

این طرح اولیه است نه نهایی، ولی شکل تصمیم را عینی می‌کند تا وقتی Claude Code شروع کرد، مسیر روشن باشد.

## بخش پنج — آنچه این تصمیم برای کار فعلی یعنی

این تصمیم به این معنی است که هیچ‌چیز از کار L0 و L1 موجود دور ریخته نمی‌شود. اتم‌های Prism فعلی (با Merkle hashing) مستقیماً به جدول atoms نگاشت می‌شوند، فقط دو ستون زمان و یک ستون embedding اضافه می‌شود. criteria_registry فعلی به جدول criteria نگاشت می‌شود، فقط جدول applicability اضافه می‌شود. و L0 و L1 موجود به‌صورت entityهایی با entity_type کشور و توسعه‌گر در گراف جا می‌گیرند، بدون اینکه اتم‌هایشان دست بخورد.

چیزی که جدید ساخته می‌شود: لایه‌ی گراف (entities + edges)، لایه‌ی معنایی (embeddingها)، جدا کردن دو خزانه، و wave تحقیقی برای ساخت entityهای JV که قبلاً فقط reference بودند.

پس مسیر روشن است و تکامل است نه انقلاب. این هم با معیار بودجه هم‌خوان است (کار قبلی هدر نمی‌رود) و هم با معیار امنیت (Merkle حفظ می‌شود).

## بخش شش — قدم بعدی پیشنهادی

حالا که معماری قطعی شد، قدم بعدی منطقی این است که schema را به‌صورت یک migration واقعی روی Supabase پیاده کنیم، با شروع از خزانه‌ی private و جدول atoms که از اتم‌های Prism موجود مهاجرت داده می‌شوند. ولی قبل از اینکه به Claude Code دستور پیاده‌سازی بدهیم، پیشنهادم این است که اول یک wave کوچک روی یک پروژه‌ی واقعی (Azura) اجرا کنیم تا schema را با داده‌ی واقعی validate کنیم — یعنی مطمئن شویم که مدل اتم-مولکول-ماده واقعاً برای یک پروژه‌ی JV پیچیده کار می‌کند، پیش از اینکه کل سیستم را رویش بنا کنیم.

این رویکرد «اول یک slice عمودی واقعی، بعد گسترش» همان چیزی است که کسب‌وکارهای موفق نرم‌افزاری برای کاهش ریسک معماری استفاده می‌کنند: به‌جای ساختن کل زیرساخت و بعد امیدوار بودن که کار کند، یک برش نازک end-to-end می‌سازی که از اتم تا ماده برای یک پروژه کار کند، و بعد که مطمئن شدی، عرضش را زیاد می‌کنی.
