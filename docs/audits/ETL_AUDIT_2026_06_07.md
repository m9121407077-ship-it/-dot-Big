## Findings

### (a) Production code requiring refactor — blocks M2

**1. Bridge atom upsert — `INSERT … ON CONFLICT (legacy_id) DO UPDATE`**

- **File:** `dot-internal-decision-pack/app/bridge_to_postgres_v0_1.py:553–564` (function `upsert_atoms`)
- **Snippet:**
  ```python
  "INSERT INTO private.atoms "
  "(entity_id, criterion_id, claim, source_id, source_class, valid_from, "
  " level, content_hash, status, evidence_quality, legacy_id, metadata) "
  "VALUES (%s,%s,%s,%s,%s,%s,%s,%s,%s,%s,%s,%s) "
  "ON CONFLICT (legacy_id) DO UPDATE SET "
  "entity_id=EXCLUDED.entity_id, criterion_id=EXCLUDED.criterion_id, "
  "claim=EXCLUDED.claim, source_id=EXCLUDED.source_id, "
  "source_class=EXCLUDED.source_class, valid_from=EXCLUDED.valid_from, "
  "level=EXCLUDED.level, content_hash=EXCLUDED.content_hash, "
  "status=EXCLUDED.status, evidence_quality=EXCLUDED.evidence_quality, "
  "metadata=EXCLUDED.metadata "
  "RETURNING atom_id, legacy_id"
  ```
- **Why it mutates atoms / why M2 blocks it:** `INSERT … ON CONFLICT … DO UPDATE` is an
  upsert. For any row whose `legacy_id` already exists, Postgres takes the **UPDATE** path,
  which fires `BEFORE UPDATE` row triggers. M2's `atoms_no_update` trigger will then
  `RAISE EXCEPTION`, aborting the whole single-transaction bridge run.
- **Where it runs against the live DB:** the committed GitHub Actions workflow
  `dot-internal-decision-pack/.github/workflows/run_bridge_production.yml` runs
  `python app/bridge_to_postgres_v0_1.py` **twice** (run #1 = commit, run #2 = idempotency
  proof). After M2: run #2 hits the `DO UPDATE` path for **all 191** bridged atoms →
  immediate failure. Likewise any future re-import, and run #1 itself for any atom whose
  `legacy_id` already exists.
- **Recommended INSERT-with-superseded_by equivalent / M2-safe refactor:** the bridge is a
  one-way mirror of the immutable SQLite source (per-row `content_hash` is deterministic and
  identical across runs), so genuine supersession does not occur during re-import. The
  minimal, append-only-correct change is to make the atoms write **insert-or-skip** instead
  of insert-or-update:
  ```python
  # atoms: append-only — never UPDATE an existing atom
  "INSERT INTO private.atoms (... , legacy_id, ...) VALUES (...) "
  "ON CONFLICT (legacy_id) DO NOTHING "
  "RETURNING atom_id, legacy_id"
  # then rebuild atom_map for rows that already existed (DO NOTHING returns no row):
  #   SELECT atom_id, legacy_id FROM private.atoms WHERE legacy_id = ANY(%(all_legacy_ids)s)
  ```
  Genuine content changes in the future must instead be a **new INSERT** carrying
  `superseded_by = <old atom_id>` (a new row, not a mutation of the old one). Note the old
  row's `status='superseded'` flip is itself an UPDATE and is therefore **also** forbidden by
  M2 — superseding the *old* row's status is out of scope for the importer and, if ever
  needed, must be modelled without mutating the retired atom (e.g. derive "is-superseded"
  from the existence of a newer atom whose `superseded_by` points at it).

> Only the **atoms** upsert is in scope for M2. The bridge issues `ON CONFLICT … DO UPDATE`
> on eight other tables too (entities, criteria, sources, missingness, contradictions,
> contradiction_statements, question_back_tickets, source_strategy_registry) — those are
> **not** affected by M2, whose triggers fire only on `private.atoms`. They are listed under
> (d) for completeness.

### (b) Historical migrations — no action

- `-dot-Big/supabase/migrations/20260606000000_initial_schema.sql:387` — `UPDATE private.atoms
  SET status='superseded', superseded_by=…, valid_to=…` inside
  `CREATE FUNCTION private.insert_atom_with_supersession(...)` (`SECURITY DEFINER`). This is an
  **already-applied** migration; the `CREATE FUNCTION` statement does not run again, and M2's
  own application is unaffected (creating triggers does not invoke the function).
  - **Latent-risk note (not blocking):** the function persists as a live DB object. If it is
    ever *invoked* after M2, its internal `UPDATE` will be blocked by `atoms_no_update`. It has
    **no active production caller** (see (c)). Optional hardening (out of scope for M2 readiness):
    `DROP FUNCTION` or refactor it to the append-only pattern in a later migration.

### (c) Test code only

- `-dot-Big/docs/verification_queries.sql:121` — `SELECT private.insert_atom_with_supersession(...)`.
  This is the function's **only** reference anywhere, and it sits **inside a `/* … */` comment
  block** explicitly labelled *"This is a demonstration; don't actually run in prod without
  backup."* It is inert (never executed), and is a verification/demonstration script under
  `docs/`, not a runtime path. Does not block M2.

## Conclusion

- **M2 readiness: BLOCKED**
- **Count of (a) items:** 1 — the bridge atom upsert (`upsert_atoms`,
  `dot-internal-decision-pack/app/bridge_to_postgres_v0_1.py:553–564`).
  **Estimated refactor effort: ~1–2 hours** — change the single atoms SQL block from
  `ON CONFLICT (legacy_id) DO UPDATE` to `ON CONFLICT (legacy_id) DO NOTHING`, rebuild
  `atom_map` via a follow-up `SELECT atom_id, legacy_id … WHERE legacy_id = ANY(...)`, then
  re-run the two-pass production-style test (the workflow runs the bridge twice) against a
  **local replica that already has the M2 trigger applied** to prove idempotency survives
  under the trigger.
- **Recommended next action:** in `m9121407077-ship-it/dot-internal-decision-pack`, refactor
  `upsert_atoms` as above (separate PR; this audit makes no code changes), verify with a
  local dry-run + idempotency re-run on a replica carrying the M2 trigger, **then** author and
  apply M2 in `-dot-Big`. Optionally, in the same M2 cycle, `DROP`/refactor
  `private.insert_atom_with_supersession` to remove the latent (currently-uncalled) UPDATE path.
  Do not apply M2 until the bridge refactor is merged and verified.
